La lógica también debe demostrar su calidad.

Una API conecta las interfaces con las reglas de negocio, los datos y los servicios externos. Verificar su comportamiento permite detectar errores, validar respuestas y reducir riesgos antes de que impacten en la experiencia del usuario.

REFERENCIA INTERACTIVA

Guía de códigos de estado HTTP

Las respuestas HTTP indican cómo procesó el servidor una solicitud. Seleccioná una familia para conocer su significado, sus códigos más habituales y su relación con las pruebas de API.

2xx — Respuestas exitosas

El servidor procesó correctamente la solicitud.

200 OK — Solicitud procesada correctamente.
201 Created — Recurso creado correctamente.
204 No Content — Solicitud exitosa sin contenido.

Perspectiva QA: un código HTTP no determina por sí solo si una prueba fue aprobada. La evaluación depende del resultado esperado. Por ejemplo, HTTP 400 puede ser correcto cuando se verifica el rechazo de datos inválidos.

01. Arquitectura de la API

El backend del portfolio está desarrollado con Node.js y Express. Expone endpoints para comprobar el estado del servicio, registrar visitantes y procesar mensajes de contacto.

  • GET /api/health: verifica la disponibilidad de la API.
  • POST /api/visitors: recibe los datos del visitante y su consentimiento.
  • POST /api/contact: valida y procesa mensajes de contacto.

Objetivo de QA: comprobar que cada endpoint responda de acuerdo con su propósito y gestione correctamente las solicitudes recibidas.

03. Persistencia de datos

SQLite almacena los registros de visitantes. Estas pruebas comprueban que los datos válidos se acepten y que las restricciones de integridad impidan registros no autorizados.

03.1. Registro válido

Comprueba que la API acepte un visitante válido y lo almacene en SQLite, devolviendo su identificador.

Resultado esperado: HTTP 201 y un ID entero.

Efecto: crea un registro real en la base de datos.

Esperando ejecución de la prueba.

03.2. Sin consentimiento

Comprueba que la API rechace el registro cuando el visitante no ha otorgado el consentimiento obligatorio.

Resultado esperado: HTTP 400 y errores de validación.

Efecto: no debe crear un registro.

Esperando ejecución de la prueba.

Objetivo de QA: verificar la aceptación de registros válidos y el rechazo de datos que incumplan las reglas de integridad.
